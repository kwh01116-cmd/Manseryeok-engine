# 사용자 제공 1950년 원문의 2400 표기 보존 — 2026-11-09 KST

## 관찰과 실패 재현

사용자가 로컬 수집 실패 뒤 원문 응답 파일 하나를 제공했다. 원문은 첨부 영역에서 비공개로 검사하고 Git에 복사하지 않았다. SHA-256은 `897f540be2a72a113cde922ad017c448accb24632d8413edcfed0eeeb60888a2`로 파일 이름의 지문과 같았다. 이는 받은 파일의 무결성 확인이며 제공 기관의 서명/원본 판본 인증이 아니다.

XML `resultCode=00`, page1/numOfRows100/totalCount24, 1950년 절기 24행이다. 두 번째 대한 행은 `locdate=19500120`, `kst="2400      "`이고 나머지 23행은 기존 HHmm 범위였다. 24행 모두 황경 필드는 없었다. 기존 코드는 공백을 제거한 뒤 시간을 00:00~23:59로만 제한해 이 행에서 `KST_HHMM`을 발생시켰다. 선행 0 누락 가설이 이번 원인은 아니었다.

처음 배포한 ZIP에 들어 있는 원래 정규화 코드를 분리해 같은 사용자 원문에 실행했고 **2번째 행 KST_HHMM**을 재현했다. API/키 문제로 해석하지 않았다.

## 최소 수정과 보장 범위

정확한 `2400`만 제공 기관 표기로 받아 **같은 원래 날짜 + time="24:00" + timeNotation="AS_REPORTED_2400"**으로 보존한다. 같은 날 00:00, 다음날 날짜, UTC 순간, 당시 한국 민간시/DST로 바꾸지 않는다. `precision=MINUTE`는 제공 표기의 정밀도이며 실제 천문 오차나 정확한 초를 뜻하지 않는다. `2401`, `2460`, `2500`, 짧은 `120`, `24:00` 문자열 등은 여전히 기존 오류로 거절한다. kst 누락은 null/DAY로 남고 완전한 분 자료가 되지 않는다.

원문 해시·receipt·출처 상태는 그대로다. 황경 누락은 기존 계약대로 null이다. `published2400Rows`를 probe/intake/전체 summary에 추가해 특수 표기를 셀 수 있다. COMPLETE는 수집 구조/완전성만 의미하며 엔진 경계 계산에 바로 쓸 수 있는 시간으로 승격하지 않는다. 비교 참조에 다음날 00:00을 넣어도 원래 날짜24:00과 조용히 일치시키지 않는다.

정규화 버전은 **0.1.1**이다. 기존 0.1.0 완료 캐시는 원문부터 offline rebuild하고 버전 라벨 외 **모든** 데이터·해시·receipt가 일치할 때만 읽는다. 0.1.0이 새 2400 표기를 포함한다고 주장하면 거절한다. 기존 년도 파일은 다시 쓰지 않고 반환/후속 export는 새로 검증한 0.1.1을 표시한다. 다른 데이터/버전 변조는 계속 거절한다.
