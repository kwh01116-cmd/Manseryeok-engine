### 겹치는 관계와 입춘 후보의 실제 차이

가상 **1990-01-01 12:00**은 己巳·丙子·丙寅·甲午다. 연주 巳와 일주 寅의 **해와 형을 모두 유지**하고, 子午의 충도 따로 남긴다. 정확한 丙 장간은 연주 본기와 일주 기타 장간이고, 같은 오행의 다른 천간 丁은 시주 본기다. 해·형이 있다는 이유로 다른 위치 근거를 지우거나 합화·길흉·강약으로 바꾸지 않았다. 화 삼합의 寅·午 부분 구성원과 화 삼회의 巳·午 부분 구성원도 별개다.

실제 API가 표시한 입춘 분인 가상 **2026-02-04 05:02**에는 두 상관 후보를 유지했다.

| 후보 | 월주·적용 절입 | 정확한 일간 己 장간 | 같은 오행의 다른 천간 | 조건과 출처 연결 |
| --- | --- | --- | --- | --- |
| `chart.candidates[0]` | 己丑 · 소한 2026-01-05 17:23 | 월주 본기 己 | 연주 기타 장간 戊 | 출생 입력과 같은 표시 분의 절입 **전 조건**. 적용 소한과 경계 입춘의 API 참조, 같은 후보의 M2 fact를 보존 |
| `chart.candidates[1]` | 庚寅 · 입춘 2026-02-04 05:02 | 연주 기타 장간 己 | 월주 기타 장간 戊 | 같은 절입의 **후 조건**. 적용 입춘과 같은 후보의 M2 fact를 보존 |

두 후보의 일간은 己로 같지만 월주·연주·장간 위치·관계는 다르다. 전 후보의 금 삼합 세 구성원과 후 후보의 화 삼합/목 삼회 두 구성원을 섞지 않았다. 첫 후보를 선택하거나 두 후보에 확률을 부여하지 않는다. [관계 겹침 전문](../../.private/m3-e3dab28-examples-20261111/overlap.text)과 [입춘 두 후보 전문](../../.private/m3-e3dab28-examples-20261111/lichun.text)도 비공개 로컬 증거다.

root와 공개 테스트 담당 agent가 일반·겹침·입춘의 한국어 본문 전체를 읽었다. agent는 입춘 전체 TEXT의 모든 fact/rule/policy/source 행도 읽어 후보별 참조와 달력·명리 출처 분리를 확인했다. 단어 정규식만 통과시킨 품질 판정이 아니다.

## 구현된 연결과 정책의 범위

명식 프로필은 기존 `kasi-api-1989-2026-local-v1`, 지원 출생 날짜는 양력 환산 **[1989-01-01, 2027-01-01)**이다. 시계 정책 `KR_API_PUBLISHED_KST_MODERN_1988_POST_DST_V1`과 기존 일주·시주 정책 네 조합을 유지했다. 기본 2026~2027 엔진과 G0 실행 경로를 교체하지 않았다.

새 명시적 M3 프로필은 `m3-structural-evidence-local-v1`, 조합/템플릿 버전은 **0.1.0**이다. [M3 정책 문서](../research/M3_EVIDENCE_POLICY_V01.md)는 다음을 프로젝트 구조적 정의와 기존 분류의 재사용으로 구분한다.

| 근거 | 실제 구현 | 남은 판정 |
| --- | --- | --- |
| 월 문맥 | 실제 후보의 일간·월주·월지 대표 오행·적용 절입·발표 분·경계 조건과 출처 | 계절 세력·사령 `UNRESOLVED` |
| 장간의 일간 관련 위치 | 같은 천간 문자와 다른 천간의 같은 오행을 별도 배열로 보존 | 유효 통근·근력·가중치 미판정 |
| 다섯 생극 방향 | 기존 오행 관계 helper를 재사용해 위치별 분류. 일주 표면 일간만 자기 중복에서 제외하고 일지 장간은 포함 | 지원 점수·비율·최종 강약 미구현 |
| 장간↔표면 연결 | 같은 천간 문자만 네 표면 위치에 연결. 여기에는 일주 표면 일간도 포함 | 전통적 투간의 효력 미판정 |
| 관계 제한 문맥 | 기존 쌍 관계와 삼합·삼회, 방향·반복 위치·겹침·완전/부분·결손을 보존 | 합화·상쇄·활성·관계 효력 `UNRESOLVED` |

새 `IMPL-M3-STRUCTURAL-EVIDENCE-V1`은 이 조합 코드의 출처다. 전통 원전의 새 신강약 판정이나 기존 학파의 승인을 뜻하지 않는다. 기존 M2의 **7개 `runtimeVersion=null`은 그대로 null**이며 새 버전으로 채우지 않았다. KASI는 달력 자료의 출처로 남고 장간·십성·지지 관계의 권위로 바뀌지 않는다. 원전 판본·권리 검토, G1-P2 NO-GO, M3 최종 해석 게이트를 유지했다.

제품 경로는 **출생 M1 한 번 → 기존 M2 한 번 → 순수 M3 → 순수 한국어 템플릿**이다. 이미 발급된 M2를 재사용할 때에는 M1/M2를 다시 실행하지 않는다. 같은 프로세스의 검증된 불변 M2만 로컬 어댑터에서 받아 후보·정책·자료와 연결하며, 외부 JSON의 status만으로 신뢰하지 않는다. 순수 모듈은 구조·참조·값의 일관성을 검사하며, 자료 인증 상태는 별도로 `inputAuthentication=NOT_PERFORMED_BY_PURE_MODULE`이라고 기록한다.

`src/domain/tenGods.ts`에서는 기존 관계 함수와 타입을 export하여 재사용했으며 함수 본문·생극 표·십성 의미를 바꾸지 않았다. 출력은 `kasi-local-m3-evidence-v1`의 `m1`, `facts`, `evidence`, `explanation`, `provenance`, `executionCounts`, `validation`으로 분리한다. 설명에서 근거 ID → 같은 후보 M2 fact/member → 기둥 위치 → rule/policy/source와 계산 자료로 추적할 수 있다.

성별·대운·as-of는 이 원국 M3 명령의 입력이 아니다. 별도의 기존 M7 선택이 달라도 같은 명식에서 M3 의미는 같음을 검사했다. 점수·신강약·격국·용신·조후·합화·길흉·개인 사건 예측, 역사시 확대, LLM, 새 화면·서버·공개 API를 만들지 않았다.

### Windows checkout의 snapshot 줄바꿈

Git의 `core.autocrlf=true`와 지정 EOL 속성 부재 때문에 새 Windows checkout에서는 두 M3 TEXT snapshot에 각각68/118개 CRLF가 생기는 것을 Git checkout 필터로 확인했다. 기존 LF 작업 트리의500/500 성공이 이 새 checkout까지 보장한 것은 아니었다. 전수 실행이 끝난 뒤 메타데이터 커밋 **cf8199a95a88f09a97e5302c231f7cff72f2cf4f**의 `.gitattributes` 두 줄로 해당 두 경로에만 `text eol=lf`를 지정했다. 같은 강제autocrlf Git필터에서 CRLF0과 원본 blob/checkout bytes 일치를 확인했다. 런타임·소스·테스트 JS·설명 내용은 바뀌지 않았다. cf8199 집중22/전체500, fail/cancel/skip/todo0과 자연exit0을 `.private/m3-lf-final-qa-20261111.json`에 기록했다. e3의 실제 데이터/CLI/브라우저 실행 기록을 새 SHA로 소급 변경하지 않는다. 줄바꿈 증거는 `.private/m3-snapshot-checkout-{before,after}-20261111.json`이다.

### 전수 실행의 자원 설정과 부분 기록

처음 두 전수 프로세스는 기본 V8 힙 설정에서 메모리가 약2GB 이상으로 커지고 진행이 느려졌다. 재검증을 생략하거나 기대값을 바꾸지 않고, 같은 소스의100쌍 검사를 Node22의 `--max-old-space-size=512`로 수행해 정상 종료를 확인했다. 이 값은 V8 old-space 상한이며 프로세스 전체 RSS가512MB 이하라는 뜻은 아니다.

먼저 UTC 소유 PID68232를 실행 파일·명령·생성 시각으로 확인해 종료했다. 마지막 기록은15,000쌍/30,746후보였으나 정확한 최종 처리 수가 아니고 완료 요약도 생성되지 않았다. CIM 종료의 기본 reason 때문에 셸 종료 코드는0이었지만 **수동 중단한 부분 실행이며 자연 완료나 PASS가 아니다**. 원래 로그와 종료 receipt를 보존했다. 새 UTC는 같은47,975쌍과 모든 검사를 힙 상한으로 처음부터 실행했다.

새 UTC가16,000쌍/33,416후보 구간까지 기존 한국 시간대 실행보다 빠르게 도달한 것을 확인한 뒤, 한국 시간대 소유 PID59404도 같은 신원 검사 후 종료했다. 이 부분 기록의 마지막 수는16,000쌍/33,416후보이고 셸 종료 코드는1이었다. 한국 시간대도 같은 상한으로 전체를 다시 시작했다. 일반 Chrome·Node를 일괄 종료하지 않았다. 중단한 두 부분 기록은 최종 집계에 합치지 않는다.

최종 두 실행의 전체 완료와 자연 종료는 위 실제 전 기간 기록에서 별도로 확인한다. 실행 코드·검증 항목·원본·정책은 바꾸지 않았고 소유 검사 프로세스의 자원 설정만 바꿨다. 상한 적용에 따른 진행 개선은 관찰했지만 정확한 GC 내부 원인을 규명했다고 주장하지 않는다. 실행 명령의 Node 옵션은 `.private/m3-e3dab28-{utc,seoul}-heap512-launch-20261111.json`, 부분 중단은 `.private/m3-{utc,seoul}-resource-restart-receipt-20261111.json`에 기록했다.

## 보존과 Git 전달 범위

검증 기대값은 검사 파일에서 읽은 값을 다시 기대값으로 사용하는 방식이 아니다. 사용자/이전 고정값을 유지했다.

시작 로컬/원격은 `00379e9143c36cc8a693166d9caaca182e64740a`였다. 범위별 구현 커밋은 다음과 같다.

새 설명 snapshot 두 개의 엄격한 바이트 검사를 유지하면서 Windows core.autocrlf=true checkout이 CRLF로 바꾸는 실제 문제를 확인했다. 원래 LF blob과 fresh Git filter 결과가 달랐고, 두 경로에만 text eol=lf를 지정한 .gitattributes 커밋 cf8199a95a88f09a97e5302c231f7cff72f2cf4f로 해결했다. 원본 snapshot 내용과 모든 실행 코드·테스트 JS·잠금 의존성은 e3dab282와 동일하다. 수정 후 Git checkout filter의 두 파일은 원본 blob과 같은 bytes/LF였고, 이 깨끗한 SHA에서 집중22/22와 전체500/500, fail/cancel/skip/todo0을 다시 실행했다. 최신 공개 검사 SHA는 cf8199a95a88f09a97e5302c231f7cff72f2cf4f이며 실제 비공개 전 기간·A·브라우저·CLI의 실행 소스 SHA는 e3dab282ae781c5385c44aa6d68ff46081781c10다. 비공개 실행 파일18개 및 A12개 불변을 근거로 문서/Git LF metadata 수정 뒤 대량 검사를 불필요하게 반복하지 않았다. 정확한 로그는 .private/m3-lf-final-full-check-20261111.log다.
