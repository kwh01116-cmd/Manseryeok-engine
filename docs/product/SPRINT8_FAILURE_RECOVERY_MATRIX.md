# Sprint 8 실패·복구 계약 v0.1

대상은 loopback에서만 실행되는 가상 주문·Fake Provider·기존 Sprint 7 생성기·암호화 파일 저장이다. 운영 DB, 실결제·환불, 실제 고객 인증·복구 메일을 제공하는 계약이 아니다. 아래는 구현이 지켜야 할 계약이며 **실제 실행 수락은 Sprint 8 실행 기록의 최종 SHA·결과와 함께 읽는다.** 테스트 시나리오가 있다는 이유로 자동 PASS를 뜻하지 않는다.

## 복구의 최소 불변식

1. 결제 수신 멱등키, 주문 생성 멱등키, 리포트 생성·저장 멱등키는 별개다. 하나의 키로 모든 실패를 처리한다고 주장하지 않는다.
2. 결과의 원국 후보·데이터 지문·역법/해석 정책·생성기/아티팩트 버전이 연결돼야 한다. 기존 S7의 LIMITED/HOLD를 결제나 재시도 때문에 승격하지 않는다.
3. 작업을 재개할 권한은 인증된 소유권과 저장소의 writer 소유권에서 나온다. 시간 경과만 보고 살아 있는 다른 프로세스의 lock을 지우지 않는다.
4. 생성 완료는 저장·검증·주문 기록의 완료를 뜻한다. HTTP 요청 하나가 성공했다거나 결제 상태가 APPROVED라는 이유만으로 COMPLETED를 표시하지 않는다.
5. 재시작 시 복구 가능한 작업이 영구 GENERATING으로 남으면 실패다. 반대로 무한 재시도도 허용하지 않는다. 3회는 이 시제품의 기술 상한이며 실제 운영 정책이 아니다.
6. 환불 검토와 테스트 환불 진행은 법적 청약철회 결론이 아니다. 실제 판매·환불은 법률·운영·PG 승인 뒤 별도 정책이 필요하다.

## 로컬 구현의 한계

암호화된 로컬 파일과 단일 writer는 운영 DB 트랜잭션·분산 작업 큐·KMS·회원 인증을 대체하지 않는다. 같은 OS 사용자가 키 파일과 프로세스에 접근할 수 있는 환경에서 악성 운영자를 방어한다고 주장하지 않는다. 결과 보관과 세션의 기술적 만료 기간은 법정 보존 기간이 아니다. 장기 로그인·소유권 복구·백업 삭제·사고 대응·실제 환불 정책은 출시 전 과제로 남는다.

결과 저장 파일과 주문 vault는 한 DB 트랜잭션이 아니다. 정상 저장 직후의 취소/환불 및 예외 경로는 결과를 삭제하도록 보완했다. 다만 `put`과 주문 연결 사이의 강제 종료가 환불과 겹치는 극단적 경우 참조 없는 암호화 파일이 남을 수 있다. 자동 sweep/백업 파기를 구현했다고 하지 않으며 운영자 정리가 필요하다. 이 파일은 주문 권한이나 정상 조회 경로로 열리지 않는다. 이미 사용자에게 전송한 문서를 서버의 권한 회수로 지울 수 있다고도 주장하지 않는다.
