# Sprint 8 — 로컬 게스트 세션·접근통제·보관 계약

이 구현은 합성 출생정보를 사용하는 **루프백 개발 시제품**이다. 실제 회원 인증, 운영 DB, PG 인증, 개인정보 법률 검토 또는 공개 서비스 보안 승인을 제공하지 않는다. `PAID_REPORT_READY`, 실제 결제와 공개 출시 게이트는 별도로 차단한다.

## 신뢰 경계

- `scripts/purchase/sessions.mjs`는 서버의 암호학적 난수로 세션 토큰·CSRF 토큰·내부 게스트 ID를 각각 발급한다. 브라우저가 보내는 `actorId`를 인증 근거로 삼지 않는다.
- 세션 토큰의 원문은 서버 저장 상태에 남기지 않는다. 별도 키의 HMAC으로 찾는 세션 색인과 내부 게스트 ID·CSRF·만료·폐기 상태를 암호화된 vault 안에 보관한다. HMAC은 익명화나 데이터 암호화의 대체 수단이 아니다.
- 브라우저에는 `HttpOnly; SameSite=Strict; Path=/` 쿠키를 사용한다. `Domain`을 지정하지 않는다. 로컬 HTTP 루프백의 개발 예외에서는 `Secure`를 사용하지 않으며, 이를 공개 HTTP 운영에 적용하면 안 된다. 공개 운영은 별도 HTTPS·쿠키·CSRF·인증 검토가 필요하다.
- 원문 토큰은 URL, 주문 ID, 화면, 로그 또는 JSON 응답에 넣지 않는다. CSRF 토큰은 동일 출처 응답에서 받아 변경 요청 헤더로 전달한다. 쿠키만 있다고 임의 주문을 조회할 수 있는 것은 아니다.
- HTTP 서버는 인증된 게스트에서 내부 actor를 결정하고, 모든 주문·작업·리포트 조회와 변경 전에 소유권을 확인한다. S7 저장소의 `actorId` 인자는 이 확인 후 서버가 주입한다. 다른 게스트의 주문 번호를 알아도 권한이 생기지 않는다.
- 세션 만료·폐기 후에는 접근을 거절한다. 기존 결과가 있다는 이유로 새 게스트에게 소유권을 이전하지 않는다. 쿠키 유실·다른 브라우저·다른 기기에서 장기 재열람을 보장하지 않는다. 회원 로그인·복구 이메일·결제 권한 연동은 이번 구현에 없다.

## 파일과 키

`scripts/purchase/vault.mjs`는 별도 지정 디렉터리에 AES-256-GCM으로 암호화한 전체 상태를 보관한다. 출생 요청은 이 상태 안에 필요한 한 번만 보관하고, 리포트 artifact는 기존 S7 `report-store.mjs`가 따로 암호화한다. 리포트에 근거 원문이 들어갈 수 있으므로 중복된 개인 정보가 전혀 없다고 주장하지 않는다.

`loadOrCreatePurchaseKeys`는 로컬 운영자가 선택한 키 디렉터리에 다음 다섯 키를 만든다. API/PG 키가 아니라 이 로컬 시제품의 저장·색인·시뮬레이터 키다.

| 키 | 용도 |
| --- | --- |
| encryptionKey | 주문·게스트·작업 상태 vault의 AES-GCM |
| indexKey | 게스트 세션 HMAC 색인 |
| reportEncryptionKey | 기존 S7 리포트 저장소 AES-GCM |
| reportIndexKey | 기존 S7 리포트 저장소 소유권·멱등 HMAC 색인 |
| providerKey | 테스트 Provider 이벤트 서명 |

키는 HTTP 정적 경로나 응답으로 제공하지 않으며 Git 추적 대상이 아니다. 키 파일 자체는 암호화하지 않는다. 같은 PC에서 자동 재시작을 검증하기 위한 개발 설정이며 운영 secret manager의 대체가 아니다. 생성 모드 `0600`·디렉터리 `0700`을 요청하지만 **Windows ACL 보장을 의미하지 않는다**. 운영 전 계정별 ACL, 키 주입·회전·복구, 백업·로그·접근기록을 검토해야 한다. 키 파일을 잃으면 복구할 수 없고, 변조·누락 파일 위에 키를 새로 만들어 정상인 것처럼 처리하지 않는다.

## 원자성·충돌·재시작

- vault는 한 프로세스에서 변경을 직렬화한다. 매 변경은 복제본에서 실행하고 JSON·상태 검증 후 임시 파일 쓰기·동기화·rename을 수행한다. 콜백 실패나 검증 실패는 기존 상태를 갱신하지 않는다. 외부 API 호출이나 비동기 콜백을 트랜잭션 안에서 실행하지 않는다.
- `writer.lock`으로 두 프로세스의 동시 쓰기를 거절한다. 기존 PID가 살아 있거나 PID 재사용 가능성이 있으면 BUSY다. 명확히 종료된 PID만 자동 회수한다. 이 확인은 운영 분산 락이나 다중 서버 트랜잭션이 아니다.
- 시작과 stale-lock 회수를 `startup.guard`로 직렬화한다. 시작의 짧은 구간에서 강제 종료되어 guard가 남으면 자동 삭제하지 않고 `PURCHASE_VAULT_STARTUP_REVIEW_REQUIRED`로 거절한다. 운영자는 실행 프로세스가 없는지 확인한 뒤 별도 복구해야 한다. 정상 실행 중 종료된 프로세스의 writer lock은 다음 시작에서 회수할 수 있다.
- 잘못된 키·ciphertext 변조·알 수 없는 상태·symlink/hardlink·비정상 파일·JSON getter/sparse/cycle는 안전하게 실패한다. 디렉터리나 키 파일을 공격자가 같은 OS 권한으로 마음대로 교체하는 상황까지 방어한 운영 보안 경계라고 주장하지 않는다.
- 실제 결제 상태를 성공으로 바꾸는 역할은 세션 인증과 별개다. 서버에서 서명 검증한 Fake Provider 이벤트와 서버의 주문 금액·통화·상품·구매자 대조가 필요하다. 성공 화면이나 임의 클라이언트 응답은 결제 증거가 아니다.

## 만료·삭제·환불

세션 기본 24시간과 리포트의 기술적 만료 상한은 **법정 보존 기간이나 최종 상품 정책이 아니다**. 세션이 만료되면 같은 저장 파일의 존재만으로 재열람을 허용하지 않는다. 명시적 리포트 삭제는 후속 접근을 거절해야 하며, 주문·환불 이력의 보존과 콘텐츠 접근 권한은 별도 상태로 다룬다. 환불 요청·완료 후 접근을 어떻게 제한할지는 테스트 정책으로 명시하고, 실제 법률상 환불 가능 여부로 표현하지 않는다.

파일 unlink는 디스크 복구 불가능한 secure erase·백업 삭제·자동 개인정보 파기 완료를 의미하지 않는다. 운영 DB·비밀키 관리·백업 삭제·실제 보존 및 파기 정책은 출시 전 미완료 과제다.

## 검증 수준

`test/sprint8-vault.test.mjs`는 암호화된 저장·깨끗한 재시작, 동시 변경 직렬화, 콜백 rollback, 잘못된 키·변조 거절, 두 writer 거절, **자식 프로세스 실제 종료 후 복구**, 시작 guard 보류, hardlink 거절, 키 재사용/오염 거절, 세션·CSRF·만료·폐기를 검사한다. HTTP 소유권·Origin/Host·권한과 브라우저 재열람 검증은 별도 서버/E2E 결과와 함께 평가한다. 이 파일의 단위 검사만으로 전체 웹 접근통제가 검증됐다고 보고하지 않는다.
